# Run Proofie yourself (judge guide)

Status: **Final cut of the hackathon submission (2026-11-01, tagged v1.0 locally); this documentation matches that cut. The kit of record is the one built from it; its hash is given with the submission, not in this file.** The manual rehearsals on 2026-10-15 and 2026-10-16 and the AI walk on 2026-10-19 described below were on RC4.2. Q1 was one focused access-redirect request (`307 Location: /disputes`): provider calls 0, suites 0, judged case NOT RUN. The deterministic W3-1 checklist arms were run on the frozen set on 2026-10-22 and again on 2026-10-24 with identical output. X3/X4 injection generalization remains a limitation; an exact held-out miss count is not established by the evidence mapped here, and no comprehensive injection-detection claim is made. The partial DR4 data-only view records three local stages observed, send and read-back NOT RUN, admission OFF; it is evidence of a local walk, not W3-4 or a judge-facing full-flow claim. Installation was checked on Windows 11 and Linux under WSL with Python 3.12; macOS is untested.

**The hosted demo, in short.** It is optional and is not the judge route. It does: the same app against the PayPal sandbox, behind an access code, in manual mode (the AI assistant is switched off there, so you type the shipment facts yourself). It does not run the local model, keep data across a restart, redeploy or idle sleep (the demo's own notice reads: "Each restart, redeploy, or idle sleep starts this demo with a fresh session. The first request after idle may take about one minute."), or use your keys. It runs on one shared sandbox account set up by the operator, whose keys live only in the hosting service's secret settings, never in this repository, so everyone who opens it sees the same disputes and uploads. The app sends data only to PayPal's sandbox; the hosting company also carries the traffic and runs the server: Render, on its free tier, from the Blueprint `render.free.yaml` in this repository. The access page says what the copy is, and each inbox row is marked "Available for a full walk.", "Already answered by a visitor." or "PayPal is not asking for evidence on this dispute now."; one page, behind the access code and linked from the inbox, shows a legacy synthetic replay fixture. It is static example data, not a recorded model output or an assistant run; nothing on that page runs or sends anything. Its address and the access code come with the submission.

**Judge mode on the hosted demo.** When the operator has listed cases for it, the hosted copy offers the page `/judge` ("Cases ready for you"). You pick one case, press "Start this case" (the page shows the exact request before you press it: PayPal's own escalate action on that sandbox case, with a fixed note), wait a few minutes and press "Check again" until the case page opens, and then follow the seller steps of section 4: shipment facts or the sample documents, generate the package, tick and approve, send, read the read-back. The case is yours for two hours; another visitor cannot take it. A pool case is used by one send, so the list can run out: the page then says so and the local route below is the way. You never clone, never enter credentials and never sit as the buyer; in our automated count this route takes 11 hands of yours, against about 65 for a local run from scratch (the wait for PayPal counts as one). Sending still needs your approval of the exact package, and the app sends once per dispute.

You run Proofie **locally, with your own free PayPal sandbox account**. We provide no credentials, by design:
- the PayPal Developer Agreement (section 1.3) does not allow us to share our app's credentials;
- nothing in this repository depends on the author's machine or accounts;
- the optional hosted demo is a second route, not a requirement: it runs in manual mode (no local model) behind an access code, against the same sandbox, and keeps no data between restarts (its address and the access code come with the submission, not with this repository);
- no secret is stored in the repository (only `.env.example`);
- everything happens in the PayPal sandbox, so no real money moves.

**Time.** The 30–60 minute estimate for a first run is not measured end to end. We timed the app part twice, both times by the author, with the sandbox already set up and the model on. On 2026-10-15 (the RC2 kit), opening the app to the first approved evidence package took 22 minutes, with two issues in the way that were fixed afterwards. On 2026-10-16 (the RC4 kit) it took 13 minutes: the assistant's answer failed its checks, so the author attached two documents and typed a statement by hand. Each time the evidence was sent under a minute after approval. The changes made since the RC4 kit (RC4.1 and RC4.2) are not re-measured. The AI session's walk of the rc4.2 kit on 2026-10-19 took about 3.5 minutes of agent time from the inbox to the first approved package; that is not a person's time and says nothing about a first run, so the 13 minutes of 2026-10-16 stays the last human figure. Most of the rest is the one-time sandbox setup (developer account, app, a test payment and a dispute) and the optional model download.

**Order of the checks.** Run `python tools/judge_check.py` right after section 2, before section 3: it works before you have a dispute, the rows that need one say so and point to section 3. Run it again after section 4, once your dispute is listed (see "Check your setup" below).

**Your own hands.** A run from scratch asks two sittings of you: your sandbox credentials and one setup command. The sandbox disputes are opened for you by one command on the seller side; if you prefer the buyer's own path, that is one more sitting as the sandbox buyer. Everything else is a command or the app's own screens. (1) your sandbox credentials; (2) one setup command (`tools/sandbox_seed.py`); the dispute then comes from one command on the seller side (`tools/sandbox_card.py`), or, on the buyer's own path, (3) one more sitting as the sandbox buyer. You type any password yourself, on PayPal's site, and the tools never ask for one. PayPal's sandbox did not let our app open the case for the buyer (the call was refused with "No permissions to set target_client_id" on 2026-11-01), so the buyer's sitting stays yours.

## 1. Install

Requirements: Python 3.12; git is needed only to clone the repository. Optional: [Ollama](https://ollama.com) (section 5).

If you received the kit as a ZIP, extract it into a new empty folder and open a terminal there: the folder that holds `README.md` is the project root, so skip the clone below.

```bash
git clone https://github.com/Josanoforo/Proofie.git
cd Proofie
```

**Windows (tested; reproducible, hash-pinned):**
```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --require-hashes -r requirements.lock.hashes.txt
```
`requirements.lock.hashes.txt` pins every package, including the test tools, to an exact version and sha256. pip refuses anything that does not match. It includes `pywin32`, so this file is for Windows only.

**Linux (tested; hash-pinned):**
```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.lock.linux.hashes.txt
```
The Linux lock includes the app and test tools, without Windows-only packages. **macOS is not tested:** create a Python 3.12 virtual environment and install `requirements-dev.txt` (version-pinned, without hashes); do not use the Windows or Linux locks as macOS proof.

On a Python version other than 3.12 the hash-pinned install can fail (on Python 3.14 pip stopped with "THESE PACKAGES DO NOT MATCH THE HASHES", observed 2026-10-17): create the virtual environment with Python 3.12.

In the rest of this guide, `python` means the interpreter of that virtual environment: `.\.venv\Scripts\python.exe` on Windows, `.venv/bin/python` on macOS and Linux.

**Offline kit verification:** This guide reports no kit-suite figure, because a figure written into the archive would change the archive it describes. No kit result replaces the human sandbox rehearsal described above. To run the offline tests of this kit yourself, use `python -m pytest tests/local -q`; expect roughly half an hour, since an AI session's dry run of 2026-10-25 took about 26 minutes while other suites ran on the same machine.

## 2. Create your sandbox credentials (PayPal Developer, free)

1. Sign in at <https://developer.paypal.com> with any PayPal account, or create a free developer account. Type your password yourself, only on PayPal's site. **A new developer account must be confirmed by e-mail** before the sandbox works, so check your inbox and spam folder.
2. In the Sandbox section you get a default **Business** (seller) account and a **Personal** (buyer) account (<https://github.com/paypaldev/getting-started-with-paypal-sandbox>). Under "Sandbox accounts" you can read their e-mails and set or reveal the passwords you will use on the sandbox site.
3. Under "Apps & Credentials" → Sandbox, create an app **owned by the Business sandbox account** and copy its **Client ID** and **Secret**. The app needs:
   - `disputes/create`, `disputes/read-seller` and `disputes/update-seller` (read and write on disputes);
   - `shipping/trackers`: the Tracking API, read for the shipment lookup and write for the one test tracker the setup script adds (section 3).

   `reporting/search` (Transaction Search) is **optional**. Proofie records a missing permission as a limitation and keeps going: if the permission has not applied yet, the app shows the limitation instead of failing.
4. Copy `.env.example` to `.env` and fill in `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`. Never share or commit `.env`. Your credentials stay on your machine: the app sends them only to PayPal's sandbox to obtain an access token, its PayPal client has the sandbox address fixed in code, a send link that points to any other host is refused, and a static test keeps the live address out of the code (tests in `tests/local/`), and the local model, if you run it, never sees them. Keep the `COPILOT_FEATURE_*` lines as supplied. This release has 75 feature settings, 72 of them enabled, including fulfilment registration, resolution writes, the contract-checks page and the ten local pages. Leave `COPILOT_FEATURE_OUTCOME_APPEAL=true`, as supplied. Four more local fronts are visible once the file is copied: open the case as the sandbox buyer (`/features/judge_as_buyer`), a buyer note (`/fulfilment/<capture_id>/buyer-note` and `/disputes/<id>/buyer-note`), a presentation guide and offline market mode (`/presentation-mode`, `/offline-market-mode/status`), and options for a package not received (`/disputes/<id>/lost-package-paths`). Enabled write features still require the app's approval and access controls. `COPILOT_RULES_COUNTRY` stays unset, so the app loads the Mexico Seller Protection rule set; `US` is the other value it ships.

## 3. Prepare your sandbox: one test payment and an "item not received" dispute

Proofie answers disputes that already exist. In the sandbox a buyer opens them by hand in the Resolution Center; creating one by API needs buyer-side credentials, which this guide does not ask of you. The setup script does everything before that step and then waits for the dispute. We ran it once ourselves (2026-10-12): the two sales were ready in under 3 minutes; the case the buyer opened on the sale with the DEMO tracker went under PayPal's review instead of the inquiry stage (step 3 below), so the dispute Proofie answers is best opened on a sale without tracking. Section 3b is the manual route we used for the pilot and for our own runs.

### 3a. With the setup script

1. The script is one file on Python's standard library (3.10 or newer): nothing to install. Run the dry run first: it prints the plan of the real run, and needs no credentials and no network:
   ```bash
   python tools/sandbox_seed.py --dry-run
   ```
2. Run it for real with a state file and an evidence folder **outside** the folder you extracted or cloned (the script refuses paths inside it, with or without `.git`), and type `SANDBOX` when it asks:
   ```bash
   python tools/sandbox_seed.py --state <private folder>/seed.json --evidence-dir <private folder>/logs
   ```
   It creates sale 1 (25.00 USD by default; `--amount-cents` changes it) and prints an approval URL: open it signed in as the **Personal (buyer)** account and approve. The script captures that payment once and adds one DEMO tracker once; then it does the same for sale 2 (15.00 USD by default; `--second-amount-cents`), captured once with **no** tracker: the sale the buyer opens the dispute on (step 3). For the tracking page of section 4, use another sale without tracking, such as a payment from section 3b. `--one-sale` skips sale 2 and then waits for the dispute on sale 1. It prints both capture ids. Credentials come from `PAYPAL_CLIENT_ID` / `PAYPAL_CLIENT_SECRET` in the environment or from `--env-file <path>` (default: the `.env` of the current folder); only those two keys are read, never printed.
3. The app's "Judge as buyer" page (`/features/judge_as_buyer`, available once the app runs, section 4) lists this route as seven numbered steps; it only guides you, signs in nowhere and opens nothing for the buyer, and once you paste your seed capture ids it marks the seeded sale in the inbox ("Opened by you as buyer — seeded sandbox sale"). The same route in short: sign in at <https://www.sandbox.paypal.com> as the **Personal** account → **Resolution Center** → **Report a problem** → that payment → **Item not received**. **Complete every step until the final confirmation screen**: an unfinished draft looks created, but it is not a dispute (this happened to us). The case id starts with `PP-R-`; paste it when the script asks. Open the case on sale 2, the sale **without** tracking; the script waits for the case on that sale by default (`--dispute-sale 1` selects sale 1 instead). In our run, a case opened on sale 1 (the one with the DEMO tracker) went under PayPal's review (`CHARGEBACK` / `UNDER_REVIEW`, with the options to accept the claim or provide supporting information) and never reached the inquiry stage, while a case opened the same day on a sale without tracking reached `WAITING_FOR_SELLER_RESPONSE` in about 4 minutes (EV-14). A case on a payment from section 3b also works: if you paste its id, the script stops with "Dispute does not match this capture; no dispute was changed" (exit code 3, no write), which is fine, because Proofie lists the dispute from your seller account on its own.
4. For the case on the selected sale, the script reads the dispute from PayPal until it is **WAITING_FOR_SELLER_RESPONSE** with a provide-evidence action, then prints "ready for seller response". It never opens, answers, escalates or resolves a dispute, and it never sends evidence.
5. If it stops (a timeout, a closed terminal), run it again with the **same** `--state` file and `--order <order id>` (and `--order2 <order id>` only if sale 2's creation ended with an unknown outcome): it reads back what already exists instead of repeating a write. It never retries a write on its own.
Alternative on the seller side, with no buyer step. The judge can open a ready-to-answer sandbox dispute with one command on the seller side: a card-funded sale with PayPal's published test card, PayPal's chargeback call and one supporting note; PayPal takes one to three minutes to prepare the case; no buyer account or login is needed. Each run creates one sandbox sale and one dispute. The command is `tools/sandbox_card.py case`; its usage, the test-card file and its exit codes are in the docstring at the top of the file (`plan-case` prints the three request fingerprints the command asks you to approve). Exit code 3 means PayPal is still preparing the case: run the same command again, it writes nothing.

### 3b. By hand

1. **Make a sandbox payment** from your Personal (buyer) account to your Business (seller) account with the order helper (a DEMO shipping address is already set):
   ```bash
   python tools/sandbox_orders.py create 4500 my-demo-dispute
   # prints an order id and an "APPROVE AS SANDBOX BUYER" URL: open it signed in as the Personal (buyer) account and approve
   python tools/sandbox_orders.py capture <order_id>
   python tools/sandbox_orders.py show <order_id>        # check the status at any time
   ```
2. Open the dispute as in step 3 of 3a. If you left a draft, open the Resolution Center again and continue it to the end; if that is not possible, start over with a new purchase.
3. The dispute must reach **INQUIRY** / **WAITING_FOR_SELLER_RESPONSE**. In our runs that took about 3 min 35 s (pilot) and about 4 minutes (2026-10-12, EV-14), each observed once on a sale without tracking; not guaranteed. If Proofie still does not list it after 10 minutes, the case was probably not submitted.

### 3c. Documents (optional)

Five ready-made synthetic documents ship in [`demo/documents/`](../demo/documents/README.md), one per scenario, each marked "DEMO DATA": a coherent delivery; a document from another order; a parcel still in transit; a document with an instruction aimed at the AI (prompt injection); an unreadable image. Their dates are generated relative to the day you run `tools/make_demo_documents.py` (section 4, step 2); the committed files carry the dates of the day they were generated.

On the seeded case the app proposes the package itself: the seller confirms it in 2 actions and types nothing. Measured once on a sandbox dispute, read-only, by the automated run.

Sending evidence consumes the dispute: PayPal moves it forward. If you want to try again, create a second dispute. We did not find in PayPal's documentation how long an unused sandbox dispute stays open.

### 3d. Open the case for the seller again (optional, sandbox helper)

`tools/sandbox_dispute_state.py` talks to PayPal's sandbox and to no other host (it checks the host in code, reads the dispute before and after every call, and writes both reads and the call to its evidence file). It sends a call only when the dispute shows the action PayPal itself offers (the matching link); otherwise it prints why and sends nothing. Passwords are never involved.

```bash
python tools/sandbox_dispute_state.py --plan <dispute id>     # one read, no write: says which helper action fits the case now
python tools/sandbox_dispute_state.py --rearm <dispute id>    # inquiry case waiting for the buyer: PayPal's escalate call
```

- **`--rearm`: no buyer click.** For a case in the inquiry stage that waits for the buyer (PayPal offers `escalate`), the helper calls PayPal's escalate endpoint. In our run on 2026-11-01 the case went to the chargeback stage, waiting for the seller with the provide-evidence action, a few minutes later, and the helper read that back from PayPal. Side effects, all PayPal's: the stage becomes CHARGEBACK, PayPal lists a note from you of type OTHER ("DEMO DATA - sandbox re-arm by escalate; no buyer action."). After it you can prepare, approve and send a package: the note the helper leaves is not counted as evidence you already sent (the setting `COPILOT_FEATURE_REARM_NOTE_IGNORED`, on in `.env.example`; it ignores a seller entry of type OTHER whose text is exactly the helper's note and that matches a 200 escalate call in your own evidence file, and nothing else). So you re-arm a fresh case with one command and run the whole seller flow once; in our walk a re-armed case was sent once and read back (the page says "Received by PayPal on ..." and "Confirmed by PayPal's own record of this dispute"). Proofie sends evidence once per dispute (section 7), and a second send on the same case is not offered. A case that already carries a real send from you is read, prepared and approved again, and its send stays closed.
- **`--lose` and `--win` call PayPal's adjudicate action** (a sandbox action) and **`--reset-seller` and `--need-buyer` call its require-evidence action** (also a sandbox action). They need PayPal's `adjudicate` or `require_evidence` link on the dispute. Adjudication goes one way: a resolved case does not reopen, so each walk that loses on purpose uses one case. On 2026-11-01 these links showed on an old case and did not show on a case that had just received evidence; when the link is absent the helper refuses and sends nothing (the three calls we made by hand without the link were answered 422 by PayPal and changed nothing).
- **More cases for more walks.** `python tools/sandbox_orders.py batch 3 1500 my-pool` creates three sales and prints three approve links: approve all of them as the sandbox buyer in one sitting, run `python tools/sandbox_orders.py capture <order id> <order id> <order id>`, which prints the single buyer click for each captured sale, and open one case per sale in the same sitting.

## 4. Run

```bash
python -m copilot.app
```
Open <http://127.0.0.1:8000/>, the address uvicorn prints; it redirects to `/disputes`. The app binds to 127.0.0.1 only and rejects non-local requests.

The key path, in order:
1. **Open your dispute** in the inbox (press "Refresh from PayPal" if it is not listed yet).
2. **Add documents**: the carrier receipt or tracking page (the synthetic ones from section 3c are read and extracted as described there). Before uploading the synthetic ones, regenerate them so that their dates are later than the sale you just created; the committed files carry the dates of the day they were generated. The script uses only the standard library and takes under a second:
   ```bash
   python tools/make_demo_documents.py
   ```
   It rewrites the five files in `demo/documents/`, document 01 delivered three days after today, with the same DEMO tracking numbers and names. On a sale without a tracker there is no tracking conflict. If a document's dates still differ from the sale (a delivery date before the payment date, or before the shipping date), the check is shown in red as "Does not match" and the review asks for a note before approval (step 4). A tracking-number or destination difference against PayPal's own data blocks approval until you fix it on the package page: that is what `02_wrong_order_tracking_and_postal_code.pdf` shows, and what any of these documents shows on a sale that already carries a tracker. You can also leave the documents out and type the shipment details yourself in the "Shipment details" form: the carrier first ("Carrier (shipping company)"), then "Tracking number (from the carrier's receipt)"; its date fields are day, month and year boxes. PayPal accepts evidence files of the types .jpg, .jpeg, .gif, .png and .pdf, less than 10 MB per file and up to 50 MB per API call (developer.paypal.com, "Supported file types and sizes", read 2026-10-16). Proofie checks the type by the file's content, not its name, refuses a file of 10 MB or more when you upload it, and refuses to attach a document that would bring one send above 50 MB.
3. **Generate the evidence package** (with Ollama the model drafts it; without Ollama you type the values in the "Shipment details" form, section 5) and read the checklist: each requirement is checked against PayPal's data and the published rules, and every statement carries a source.
4. **Review each statement and approve** (the button in the package page's next-step panel): every statement is shown in full with its source document, field and reading, above one approval that names their count ("Approve this package: I have read these N statements"). The approval is bound to a hash of those exact N statements and any change voids it; the send is a separate click. A tracking-number or destination difference against PayPal's own data blocks approval until you fix it on the package page. A date difference between a document and the sale is shown in red ("Does not match the source") and does not block on its own: the review lists it under "Open notices: explain your decision", together with any document the app could not read, and asks for a one-line note before approval; the note is kept on the receipt and shown on the print view. If the tracking evidence names no carrier, the review page shows "Cannot approve yet" and asks you to pick one ("Choose the carrier"), because PayPal rejects evidence with no carrier. At or above a review threshold (USD 750.00, MXN 10,000.00), or when the amount or currency is unknown, the page also asks you to type `I REVIEWED EACH CLAIM`. Approving records a local receipt with the content hash and sends nothing; you return to the package page, which shows "Package approved" and the next step, "Send evidence to PayPal" (the step says "Sending to PayPal cannot be undone; Proofie sends it once.").
5. **Print or send.** The print view at `/disputes/<dispute id>/packages/<n>/print` is a local snapshot for your records and sends nothing; its "Case file record" block names the source commit, the send record, the package hash and the approval fingerprint the send was checked against, and what PayPal's record lists, and "Download the case file" gives one zip you can check offline (section 7). Its link reads "Print the evidence package", and "Save a copy of what you sent" on a version that was already sent). "Send evidence to PayPal" on the package page is what sends the evidence, and it is yours; the four write pages below follow the same rule. Nothing is sent on its own.
6. **Check what PayPal shows.** After the send the app re-reads the dispute and shows the headline "Evidence sent to PayPal" and the tag "Received by PayPal (confirmed by reading the dispute back)" when the read-back finds the evidence there, and lists "What PayPal's record lists": the evidence type, the date PayPal gives it and the names of the documents PayPal lists with it (a send recorded before this list was kept says so and points to the dispute). The package page of that version then reads "Evidence sent to PayPal." and "This version cannot change.", and, while PayPal lists evidence from you, the sentence above in place of any new-version button.

**The case workspace.** Each case opens in the v3 case workspace: an overview and task views for reviewing the claims, preparing and checking the evidence package, approving it, sending it and keeping the records. The case bar shows three links (Overview, Review claims, and Evidence package or Prepare package) and a closed "Other case links" block. The pages one level down (history, ledger, draft, call script, two clocks, first guide, lost package paths, buyer note, third-party statements and the fulfilment moment) are three clicks from the overview: open "Other case links", open the task page, then follow its link. Every one of them is linked from a task page; this release does not offer them in two clicks.

Other pages in this release (open by link where one exists, otherwise by URL):
- `/disputes/<dispute id>/triage`, "What the evidence supports" (link on the dispute page), and `/disputes/<dispute id>/ledger`, "What this app recorded" (link from triage);
- `/account`, where the account stands against PayPal's high-volume dispute fee (link in the inbox), and `/deadlines`, "PayPal due dates" (the inbox shows its banner link only when a case has under 3 days left or is past its due date; otherwise open it by URL);
- the dispute page, next to "Respond by": while PayPal's due date has not passed, the link "Add the due date to a calendar (.ics file)" downloads one small calendar file, `proofie-due-<dispute id>.ics`, with PayPal's own due date and a reminder 24 hours before it. The app makes one read of the dispute to make it, changes nothing at PayPal and stores nothing in its database (the read is logged like every PayPal call), and the file stays on your computer until you open it in a calendar. If PayPal gave no due date, the link does not show, and a typed address answers "No due date to add";
- the dispute page, "PayPal's timeline": the dated items of PayPal's dispute record (opening, evidence, messages, offers, adjudications, money movements, contact times, last update), each with its time in Mexico City time and the line "As PayPal's record reads at <time>."; PayPal's record has no log of status changes, and the page says so.
- the package page, with the United States rule set (`COPILOT_RULES_COUNTRY=US`): a check that comes from PayPal's published terms has a "PayPal's words" disclosure in its row, with the quoted clause, its source and the link to the full terms on PayPal; a check that is Proofie's own rule says "Proofie's own rule", and one from the case request says "PayPal asked for this". The Mexico rule set (the default) shows no quoted clause yet.
- the package page, with the Mexico rule set (the default): "Spanish version of your statements" lists each English statement with a form to type its Spanish version ("For your own review in Spanish. PayPal receives the English statements only; the Spanish version stays in Proofie. Approving the package covers the English and the Spanish text."); a button asks the local model to draft the missing versions when the model is on (it can be wrong: code checks that numbers, dates and tracking codes match the English, and you review every word; in the hosted demo the model is off and you type each version); a statement changed afterwards is marked so, and saving a Spanish version clears a valid approval, as an English edit does.
- `/events/state`, "What PayPal last showed": the status the event reader recorded for each dispute, and when (this release runs no event reader, so the page says "No verified observations have been recorded here yet."); `/disputes/<dispute id>/packages/<n>/claims-review`, "See where each statement comes from" (the statement sources on their own); `/disputes/<dispute id>/outcome`, a read-only view of the result (the appeal call is on but appears only when PayPal offers an appeal; it has not been exercised against PayPal).

The write pages of this release, each with the same rule as the evidence package: you see the exact request, and nothing reaches PayPal until you approve it there.
- `/disputes/<dispute id>/resolution`, "Resolution options and buyer messages": the options PayPal offers with their economics, then "Actions, in this order": an offer form and a message form, each shown only when PayPal's latest response offers it (sending a message ends the chance to make an offer, and the page says so). "Review the offer" / "Review the message" opens a separate check page with the exact request and its fingerprint; there approving is the send: "Send offer to PayPal" or "Send message to buyer" sends it once and opens the sent page, which reads the dispute back once PayPal has accepted it (EV-12, EV-15 and EV-18 in the evidence index: the read-back after a message and after an offer, on earlier builds). "What this app recorded" below keeps every request and the status PayPal returned.
- `/disputes/<dispute id>/resolution/accept-claim/...`, "Review accepting the claim" (the last control on the resolution page, offered while PayPal's fresh read shows the action): the check page states the consequence and PayPal's amount and currency, you type the amount phrase and approve the request by hash, and the send is a separate click followed by a read-back. On the hosted copy it is allowed on the judge's own pool case and refused on every other case.
- `/disputes/<dispute id>/draft`: the message to the buyer first, starting as a fixed template, then the facts built by code from PayPal's data; with Ollama, "Ask the local assistant for a draft (English and Spanish)" shows the assistant's text in a separate section, marked as written by AI; it enters your message only if you choose "Use this AI text as my starting point". "Review this text on the resolution page (nothing is sent yet)" hands it to the resolution check page ("Review the message before it is sent"), where you approve it; the draft page sends nothing.
- `/fulfilment` and `/fulfilment/<transaction id>`, "Tracking at the sale": prepare the Add Tracking request for a sale before any dispute exists. The form asks for the carrier first ("Carrier (shipping company)"), then "Tracking number (from the carrier's receipt)"; "Review what will be sent" opens a separate check page that shows the request exactly, and "Add tracking in PayPal" there sends it once: on that page approving is the send. The result page's headline names the outcome (for example "Tracking registered in PayPal"). The file keeps the request fingerprint and PayPal's answer (EV-13 and EV-16 in the evidence index, on earlier builds: the POST and the read that lists the tracker carry the same fingerprints). Above the form the page says whether PayPal already shows tracking for that sale; below it, a folded block "What PayPal requires for this sale" lists the delivery requirements of the loaded Seller Protection rule set, each with its citation and source link, the signed-receipt line, and what PayPal also requires that Proofie does not check. The block says it is information from PayPal's published programme and does not decide whether protection applies; only PayPal decides.
- `/delivery-facts/<transaction id>`, "Shipment facts" for that sale: the saved copy of what you entered and what PayPal returned for that tracking registration, with the differences between the two named; it asks PayPal nothing when opened. Before a file exists it answers "No local delivery facts for this capture".

**To see the four pages, in this order.** The links: the site header shows "Tracking at the sale" and the inbox shows "Tracking at the sale: files" at the bottom (both to `/fulfilment`); the dispute page shows "Resolution options and buyer messages" and "Draft a message to the buyer"; the resolution page shows "Local delivery facts for transaction <id>" once a local tracking file exists (before that: "Local delivery facts: available after a local tracking file has been saved."); `/fulfilment/<transaction id>` is reached from `/fulfilment` with "Open the sale". Typing each URL also works. 1. `/fulfilment`, then `/fulfilment/<transaction id>` with the capture id of a sale that has no tracking yet and no open dispute (the setup script's first sale already has one; if you opened your dispute on its second sale as section 3 suggests, use a payment from section 3b here, or stop at the check page that "Review what will be sent" opens, without pressing "Add tracking in PayPal"): on that check page approving is the send, once. 2. `/delivery-facts/<transaction id>` for that same id: the page exists only after step 1 saved a file; before that it answers "No local delivery facts for this capture". 3. `/disputes/<dispute id>/draft` for the open dispute: the fixed template and the facts appear without Ollama; "Review this text on the resolution page (nothing is sent yet)" takes the text to the check page of step 4. 4. `/disputes/<dispute id>/resolution`: the offer form and the message form appear only while PayPal's latest read of the dispute offers them (in our sandbox runs a fresh "Item not received" dispute in its inquiry stage did; sending a message removes the offer option); "Review the message" opens a check page with the exact request, and "Send message to buyer" there sends it once and opens the sent page. Until `.env` holds your sandbox credentials, every one of these pages answers "PayPal sandbox credentials are not set up yet" except `/fulfilment` and `/delivery-facts/<transaction id>`, which only read local files.

This release includes the AI message draft, delivery facts, fulfilment registration, resolution offers and messages, the contract-checks page (`/conformance`), PayPal's own timeline of a dispute (the dated items its record gives, behind `COPILOT_FEATURE_TIMELINE`), PayPal's own words behind each check for the United States rule set (a quoted clause with its source, behind `COPILOT_FEATURE_CLAUSES`; the Mexico rule set has none yet), a Spanish version of each statement for the Mexico rule set (behind `COPILOT_FEATURE_BILINGUAL`): typed by the seller or, with the local model, drafted by it and reviewed by the seller, with code checking that numbers, dates and tracking codes match the English (the hosted copy: typed only); approving covers the English and the Spanish text, and PayPal receives the English statements only; a downloadable case file of a package (a zip with the print view, the files and a manifest of hashes, checked offline with `python -m copilot.verify --case-file`); and, in the hosted demo only, a legacy synthetic replay fixture, not a recording of a model run. Write actions remain subject to the app's approval and access controls. The appeal call is on: it appears only when PayPal's fresh read of the dispute offers an appeal, and it is sent once after the seller approves the exact request. It has not been exercised against PayPal, because no sandbox dispute of ours has offered an appeal. Webhooks (the "PayPal notices" page) and webhook verification are off in the published `.env.example` and on only in the hosted copy's Blueprint, pending the owner's registration of its address. The published `.env.example` contains 75 feature settings: 72 enabled; `COPILOT_FEATURE_DEMO_DOCUMENTS=false`, `COPILOT_FEATURE_WEBHOOKS=false` and `COPILOT_FEATURE_WEBHOOKS_VERIFY=false` are off.

Ten more local pages are on by default; the README lists them under "Ten more local pages, on by default", and none of them sends anything to PayPal. Two are the quickest way in: `/features/judge_walkthrough` follows one synthetic case from the inbox to its saved package, and `/features/local_demo_hub` lists the ten pages with their flag state and links to them; in the kit its claims table shows "unavailable" for the lane's private source and receipt records, which are not shipped. The hosted copy shows the local MCP contracts page, which only describes that stdio server; the server itself runs on your machine, not on the host.

Your local copy has no webhooks: they need a public HTTPS endpoint, which it does not have. The hosted copy is the one exception, and it is pending: its Blueprint switches the receiver and its verification on, but the owner has not registered its address in the sandbox app yet, so until he does it receives no events. Once he does, each verified dispute event appears in the dispute's timeline as "PayPal notified Proofie at <time> (verified)", with the status of Proofie's own read of the dispute and never the event's own; the free instance sleeps (PayPal retries an event that times out), events are lost on restart, and the sandbox account is shared. Press "Refresh from PayPal" (inbox) or "Check again" (dispute page) to re-read the dispute from PayPal. The inbox does not reload itself: while a draft is being prepared it says so and shows a "Reload to see progress" link.

## Check your setup

One command checks your own setup and prints a table (step, expected, seen, PASS/FAIL, how to fix) and a one-line verdict:

```bash
python tools/judge_check.py
```

It looks at your Python and virtual environment, whether `.env` holds both sandbox credentials (it says only whether they are set, never their values) and the `COPILOT_FEATURE_*` lines as supplied in `.env.example`, and whether the app answers on port 8000; if it does not, the check starts it with `python -m copilot.app` and stops it at the end (`--no-start` leaves that to you, `--port` names another port). Then it lists your sandbox disputes through the app, picks one that is waiting for your response in the Inquiry stage and opens every seller page of that dispute once, expecting a 200 and the page's heading. If you have no such dispute yet, that row says so and points to section 3; it is the next step, not an error. It sends only GET requests to the local app: nothing is written to PayPal, and it needs no browser. It exits with 0 only when every row passes. It is a check of your own setup, not a test suite, and it reports no test figure.

## 6. What goes through PayPal's REST API, and what through MCP

- **The app uses the PayPal REST API only**, through one sandbox client whose base URL is fixed to `api-m.sandbox.paypal.com`: list and read disputes, Transaction Search, tracking, and the evidence send (`provide-evidence`).
- **Proofie is also an MCP server, optional and local** ([docs/MCP.md](MCP.md)). A seller's AI assistant (for example Claude Desktop) can list disputes, read a dispute file, see what is missing and prepare a **draft**. Approval stays a button in Proofie's web page; the MCP server has no approve tool. The contrast with PayPal's own agent toolkit (`github.com/paypal/agent-toolkit`, its README's "Dispute Management" list, re-read 2026-10-17): its dispute tools are `list_disputes`, `get_dispute` and `accept_dispute_claim`, so an assistant wired to it can watch a seller's disputes and concede them, not defend them. Through Proofie's server an assistant can list, read, see what is missing and prepare a draft; it cannot approve, cannot send unless the seller enables the send tool and has approved that exact content, and cannot accept a claim.
- **Our video also shows PayPal's own official MCP server** (from PayPal's AI Toolkit) next to Proofie's, with Claude as the client: PayPal's server reads the dispute, and Proofie builds the evidence file. That demo needs a PayPal MCP access token that we never ship. You do not need it to judge or run Proofie; everything above works without it.
- **The MCP server and the assistant are not part of the hosted demo.** The hosted copy is the web app only, in manual mode; the MCP server runs on your own computer, from your own copy ([docs/MCP.md](MCP.md)).
- **Proofie's local model does not drive MCP tools.** In the demo, the MCP client is Claude.
- **Where Proofie meets PayPal's published integration guidance and where it deliberately deviates** is listed point by point, with the public source and read date of each point, in [docs/CONFORMANCE.md](CONFORMANCE.md).

## 7. Things to know

- **Evidence is sent once per dispute.** Proofie sends evidence once per dispute: it never sends when PayPal already lists evidence from you for that dispute. The pages say it: when PayPal's read lists evidence from you, the package page and the dispute page read "PayPal already lists evidence from you for this dispute. Proofie sends evidence once per dispute and will not send again." under their next step, with a link to PayPal's Resolution Center (sandbox), and they offer no send, approve, new version or mark. This also covers a send that reached PayPal with a file missing: Proofie does not send again, and you continue in PayPal's Resolution Center.
- **Attached files are confirmed by name and count.** PayPal's record lists a document by its name, not its contents, so after a send Proofie counts a file as present when its name appears in PayPal's read-back at least as many times as it was attached, and it refuses to attach a second file with the same name to one package ("Cannot attach this file": detach the other file first, or upload this one again under another name). How PayPal lists two same-name documents was never observed.
- **Sandbox only.** The app's PayPal client has the sandbox host fixed in code, a send link to any other host is refused, and a static test keeps the live host out of the code (tests in `tests/local/`).
- **Deadlines.** PayPal's help for sellers (HELP1083, read 2026-10-16) says you must respond within the first 10 days after a dispute is created; if you do not and the buyer escalates it to a claim, PayPal resolves the case in the buyer's favour. The dispute's `seller_response_due_date` is the date by which the seller must respond to that case. A due date is shown, in Mexico City time, only when PayPal's response carries that field; otherwise the page says "No verified deadline available". Status is read back from PayPal, not pushed by webhooks, in this release (section 4).
- **Records.** A buyer can open an "Item not received" dispute within 180 days of the date of the payment (HELP1173, read 2026-10-16): keep the records of orders, shipments and messages at least that long.
- **Issuing a refund outside a dispute stays in PayPal's Resolution Center; accepting the claim is available in Proofie as the seller's last option.** Accepting the claim has a check page of its own that shows PayPal's refund amount and currency and the sentence "This refunds the buyer and closes the dispute. Proofie cannot undo it."; you type the amount phrase, approve the exact request by hash and send it as a separate click. It is offered while PayPal's fresh read of the dispute shows the action, listed after the offer, the message and the defence, and the model never suggests it. On the hosted copy it is allowed on the judge's own pool case and refused on every other case. The one escalation it can make is a sandbox-only judge re-arm by PayPal's escalate link, approval-bound, in the helper script or the hosted demo's own button, never in the seller's flow; the resolution page never escalates. The resolution page prepares an offer, a refund offer that PayPal's make-offer sends for the buyer to accept (REFUND is the only offer type the sandbox lists), or a message to the buyer; its check page shows the exact request and sends it once, only after you approve it there; issuing a refund outside a dispute stays in PayPal's sandbox Resolution Center, and accepting the claim is the seller's last-resort option in Proofie, shown only when PayPal offers it and sent after the seller's own approval; the assistant has no tool to approve, send or accept a claim.
- **Check a downloaded case file.** `python -m copilot.verify --case-file <zip>` checks the zip on its own, with no database and no web code: every member against the manifest (`MANIFEST.json`, schema `proofie.case_file.v1`), the source commit the file names, the package hash and the approval fingerprint recomputed from the request it holds, and each attached file; it refuses members that are not listed or not safe, and exits 0 when everything matches, 1 when a check fails and 2 when the file cannot be read. The tests change one thing at a time (a file's bytes, the print view, the request, the approval, the attachment list, an extra member, a missing member, the source commit) and the check fails each time. A matching hash shows the content is unchanged; it does not show that what it says is true.
- **Check your stored files.** `python -m copilot.verify` recomputes the sha256 of every stored document and compares it with the hash recorded when it was uploaded and with every package that attached it; it prints one `OK` or `FAIL` line per document and a `TOTAL` line, exits 1 if any check fails (2 if there is no readable data folder), and opens the database read-only (it changes nothing). `--data-dir <folder>` points it at another data folder.
- **Contract checks.** `/conformance` ("Contract checks") compares the request bodies Proofie's own code builds with minimal extracts of PayPal's published OpenAPI documents (sources and hashes in [THIRD-PARTY.md](../THIRD-PARTY.md)). The page says what it is in plain words: a paragraph that starts "What this means" (the checks run on this computer, contact no one and do not check your disputes, and you do not need to do anything), two labelled lines: "Schema used" reads "the short extracts of PayPal's published documents built into Proofie" while `PROOFIE_SPECS_DIR` is not set or not a folder, and "PayPal's full published documents, set up on this computer." when it points to a folder; "Responses checked" reads "Proofie's own sample responses, not responses from PayPal" while `PROOFIE_EVIDENCE_DIR` is not set, and when it is set it counts the recorded PayPal responses found there, or reads "none. No recorded PayPal responses were found on this computer." when nothing usable is found, a table captioned "Proofie's requests compared with PayPal's published API documents" with one row per request, each marked "matches", "differs" (with the field named) or "no schema to check", a last row "All request checks" with the counts (for example "1 differs" or "1 has no schema to check", worded by count), a line "The DOMINO carrier, as sent in the evidence request and in the appeal" with its own count, and a closed "Technical details" block. It makes no network call.
- **Local data.** The database and uploads live under `data/` (git-ignored). Each PayPal call is logged, sanitised, to `evidence/*.jsonl` in your copy (created on first use). Those logs hold your own sandbox data: do not commit or share them. Delete both folders to start fresh. Under the PayPal Developer Agreement (last updated 2024-11-18), section 11.1, information received through an API call is PayPal's Confidential Information: that is why these logs stay on your machine and why this repository publishes no PayPal response bodies.
- **Actions appear only when PayPal's latest response offers them.** A dispute in `UNDER_REVIEW` usually offers none, so the page shows no seller action. PayPal's sandbox provides test-only helpers to change a dispute's status (see "update dispute status" in the Disputes API reference, <https://developer.paypal.com/docs/api/customer-disputes/v1/>). Using them is outside this app; section 3d describes the helper script that calls them with their guards. A new dispute is always an option.
- **A read-only status link for the buyer (optional).** `/status-link` makes a page the buyer can open without an account: you type the item, the carrier, the tracking number, the status and the date you registered the tracking with PayPal, you see exactly what the buyer will see, and you approve it. The link is signed with a key the operator sets (`COPILOT_STATUS_LINK_KEY`, 32 characters or more; without it no link is made), works for 14 days, carries no case number, and shows no buyer name, address, e-mail or amount. The page makes no PayPal call and has no reply form; talking to the seller stays in PayPal's Resolution Center. A hosted copy serves this one read-only path (`/s/<token>`) without the access code only after its operator has set the key; until then the path answers 404, and everything else still needs the access code. Step 9.4 of `tools/auto_run.py` walks it: the forms create a link and a fresh browser with no cookies opens it.

## 8. Troubleshooting

Messages below are taken from the app's code, first checked on 2026-10-05 after the first-run fixes and re-checked against the RC4.2 code on 2026-10-18; the delivery rehearsals re-check them on a clean copy:

- **No `.env`, or `.env` still holding the `.env.example` placeholders** (`your-...-here`): a page titled "PayPal sandbox credentials are not set up yet" explains how to copy `.env.example` to `.env`, fill in both values, restart the app and reload. Placeholders count as missing, so an untouched file never reaches PayPal. Nothing was sent. The page is served with HTTP status 503.
- **Wrong `.env` credentials** (PayPal answers 401 or 403): a page titled "PayPal rejected the app's credentials" asks you to check `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` in `.env`; no value is shown. Use your own sandbox app's values, not the placeholders from `.env.example`.
- **PayPal unreachable** (network error, PayPal 5xx or 429): "PayPal could not be reached right now", with an invitation to try again. Nothing was changed.
- **Any other server error:** a page "Something went wrong inside Proofie" with a way back; the console logs only the method, path and error type.
- **"Your session expired"** (403, on any button): the action was refused and nothing was changed. Go back and try again. If it keeps happening, check that your browser allows cookies for this site (127.0.0.1), reload the dispute page and repeat the action.
- **"Cannot approve yet".** The review page says why: a statement asserts delivery without a source backing it, a document conflicts with PayPal's data, or the tracking evidence names no carrier ("Pick a carrier: PayPal rejects evidence with no carrier"). Fix it on the package page and approve again.
- **No Send button.** Send is offered only when the package has a tracking number. The package page says "none yet, so this cannot be sent" next to the Tracking line, with a link to type the number or upload the carrier's document. After a "Check again" with an uncertain result, Send also stays hidden until PayPal's state has been read.
- **Generate seems slow.** Under the button: "Preparing with the assistant. This can take a few minutes. Keep this page open." (in the hosted demo: "Preparing the package. Keep this page open.") The inbox marks the row as preparing and shows a "Reload to see progress" link; it does not reload itself.
- **AI output that fails validation:** the package page shows "The assistant's answer could not be checked"; continue by hand.
- **PDF upload without the PDF reader library:** "The PDF reader is not available on this computer", and the file is not added. Reinstall the requirements (section 1).
- **No disputes yet.** The inbox shows "No disputes need your attention right now". This is not an error: create one first (section 3).
- **Ollama not running or not reachable.** "Generate evidence package" shows the manual-mode notice from section 5. The inbox's automatic preparation falls back the same way.
