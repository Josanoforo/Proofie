# Conformance: Proofie against PayPal's published contract

Status: **Shipped with the v1.1.1 cut. Every row is as of the date it names; the last full re-read against the code was on 2026-10-18; accept-claim, tracking registration and the judge case came after it, and row 17 describes accept-claim.** First prepared 2026-10-10; section 4 refreshed 2026-10-12 after the three write operations each ran once through the app in the sandbox (on earlier builds of this feature set); the rows about `PayPal-Request-Id`, retries and the send-once guard were checked against the code and rewritten on 2026-10-17 after a sandbox observation of 2026-10-16, and were read again against the merged code on 2026-10-18. That re-read changed: row 4 (the token cache lives in one short-lived client per request, verdict "partly meets"), row 5 (the OAuth token request is the one POST without a request id; both send-once guards named), row 7 (no automatic retry means "the app never retries a write on its own", the published probe that retries on purpose is named, the evidence attempt registry and its two-minute takeover are named, and evidence is sent once per dispute because PayPal listing evidence from the seller refuses any further send), row 8 (guards named), row 12 (the webhook code is present behind a setting that is off), row 13 (verdict "partly meets": `allowed_response_options` is not read), row 16 and the provide-evidence row (attached files confirmed as a multiset of listed names), the send-message row (the link or e-mail marker check, at most two reads per pending row each time a page is opened and one per Check again, confirmation only when PayPal lists the message, 80 seconds to settle), the make-offer row and the appeal clause (which guard each write uses). Rows 5, 7 and 8 and the send-message row were checked once more on 2026-10-18 against the final send code (the send service, the write guard, the attempt registry, the send routes and the four writes): the behaviour they describe is unchanged, the last changes to the send code only chose the wording of answers by the fresh read and added no guard, ordering, write or registry change, and no row quotes an answer of the app; every other row is as of the date it names. This edit adds no new read of PayPal's documents. Every row names its public source and the date we read it. This page makes no claim about any other product, and no claim about reliability or outcomes: it says where Proofie's requests match PayPal's published documents, where they match what the sandbox actually answered, and where Proofie deliberately does something else and why.

## 1. The one-sentence result

Proofie's request bodies were validated against PayPal's own published OpenAPI documents (the `schema.json` files on `developer.paypal.com`, pinned on 2026-10-06 by sha256, listed in section 5), and the responses it recorded from the sandbox were checked against the same documents. Every operation Proofie calls exists in those documents; every field name, enum value and bound it sends to the tracking and Transaction Search operations is in the schema, and the dispute evidence send uses the JSON part that the contract's prose describes but its schema does not define (section 4); every field it reads from a dispute, transaction, tracker or order response exists there. Of 142 recorded 2xx sandbox responses, 62 showed no difference other than our log sanitiser's own placeholders, and the rest differ only where PayPal's sandbox and PayPal's contract disagree with each other (fund-movement enums, empty search results, the number of tracker links and the tracker wrapper); nothing Proofie reads is affected. One latent exception found on 2026-10-06 (a catalogue carrier code that the dispute contract's `carrier_name` enum does not list) was closed on 2026-10-08: that code is now sent as `OTHER` with the carrier's name, as the contract requires.

## 2. PayPal's integration guidance, point by point

Source: the dispute, authentication and webhook references and the integration "doctor" checklist of PayPal's public plugin for coding agents (repository `paypal/AI-Toolkit`, v1.1.0, files `references/disputes-refunds.md`, `references/authentication.md`, `references/webhooks.md`, `commands/doctor.md`, `skills/paypal-best-practices/SKILL.md`), read on 2026-10-06. The plugin was never installed; we read its files. "Meets", "partly meets" and "deliberate deviation" are design statements about Proofie, checked in its code: "meets" means the code does what the reference asks, "partly meets" that it does part of it (the row says which part), "deliberate deviation" that it does something else on purpose.

| # | PayPal's point | Proofie | Verdict | Where in Proofie |
|---|---|---|---|---|
| 1 | No secret hard-coded outside an environment file; no credentials in front-end code | Credentials come only from `.env`, read by the sandbox client; a secret scanner runs before every commit and again at export; the web pages carry no credential | meets | `pilot/client.py`, `tools/scan_staged.py` |
| 2 | `.env` must be git-ignored | `.env` is git-ignored; only `.env.example` is tracked | meets | `.gitignore`, `.env.example` |
| 3 | Warn when `.env.example` exists but `.env` does not | On a fresh clone that is the expected first state: judges bring their own sandbox app; the app shows a plain page explaining how to create `.env` and never calls PayPal with placeholders | deliberate deviation (the warning is the design) | `docs/JUDGE-RUN.md` section 8 |
| 4 | Cache the access token and honour `expires_in` | Each client keeps its token in memory and asks for a new one 60 seconds before `expires_in` (`pilot/client.py:236-262`). The web app builds one short-lived client per page request and the MCP server one per tool call (`copilot/web/routes_disputes.py:56-62`, `copilot/mcp_server.py:81-83`), so in practice each request asks PayPal for its own token and the cache only serves the several PayPal calls inside one request | partly meets (the cache and the expiry rule exist; the token is not kept between requests) | `pilot/client.py`, `copilot/web/routes_disputes.py`, `copilot/mcp_server.py` |
| 5 | Send `PayPal-Request-Id` on every POST | Every POST to a PayPal API resource carries one, logged with the call (the OAuth token request is the one POST without it, `pilot/client.py`): evidence, message and offer derive it as a UUIDv5 from the dispute id and a hash of the approved request (for evidence, the statements and the tracking; the attached files only for a send that takes over another package's refused attempt), and the tracker from a hash of its body, which names the sale; so the same content carries the same id. The setup scripts use a random one. Proofie does not rely on it to prevent a duplicate: in the sandbox PayPal did not deduplicate `send-message` by it (observed 2026-10-16), so the app's own send-once guards refuse a repeat send of the same approved request (the reservation of `copilot/core/write_guard.py` for a message, an offer and a tracker; the attempt registry of `copilot/core/attempt_store.py` for evidence; rows 7 and 8, and the send-message row below) | meets (the header is sent; the duplicate guard is Proofie's own) | `pilot/client.py`, `copilot/core/write_guard.py`, `copilot/core/attempt_store.py` |
| 6 | Log `debug_id` | Logged for every call, taken from the header or the body | meets | `pilot/client.py` |
| 7 | Retry 429 with exponential backoff | The app never retries a write on its own, by design: one call per write, and the answer is kept and shown (the published probe `pilot/step2_order.py` retries a capture on purpose, to test PayPal's idempotency; it is a probe, not part of the app). After a 429, a 5xx or a lost answer the outcome counts as unknown, and the app does not send the same approved request again, except after a definite refusal (a 4xx other than 429), which frees the request for a new approval (`_definite_refusal` and the reservation `finish` in `copilot/features/resolution/service.py`, `write_guard.py`; for evidence a `failed` or `blocked` row can be taken over, `send_service.py`). A message or a tracker (the reservation of `copilot/core/write_guard.py`) is released only by a complete read at least 10 minutes after the POST that does not list it; an offer is not released by a read (a changed offer is a different request). Evidence (the attempt registry of `copilot/core/attempt_store.py`: an atomic claim under `BEGIN IMMEDIATE`, and the `sent_unconfirmed` row written before the POST): the same package is not sent again, and an attempt left `pending` (claimed, no POST) is taken over only when it is older than two minutes and after a fresh read (`PENDING_RECLAIM_AFTER_SECONDS` in `copilot/core/send_service.py`). Proofie sends evidence once per dispute: `check_preconditions` (`pilot/step5_send_evidence.py`, applied in `send_service._send_locked` before any POST) refuses to send when PayPal already lists evidence submitted by the seller, so after a send that reached PayPal, even one with some files missing, nothing more is sent and the seller continues in PayPal's Resolution Center. If the earlier send is not at PayPal at all (PayPal lists no evidence from the seller), the seller can record that on the package page and a changed package (a different statement or tracking) can go out | deliberate deviation (evidence discipline: nothing is re-sent without a human) | `copilot/core/send_service.py`, `copilot/core/attempt_store.py`, `copilot/core/write_guard.py`, `pilot/step5_send_evidence.py` |
| 8 | Retry 500 with the same idempotency key | Same as 7: the app never retries on its own. After a 500 the outcome counts as unknown, and the rule of row 7 applies. Reusing the id is not what makes a retry safe: PayPal did not deduplicate `send-message` by it in the sandbox (observed 2026-10-16) | deliberate deviation | `copilot/core/send_service.py`, `copilot/core/attempt_store.py`, `copilot/core/write_guard.py` |
| 9 | Do not hard-code the sandbox URL; add an environment switch | The sandbox host is the client's constant (`pilot/client.py`), the send path accepts only that host (`copilot/core/send.py`), and a static test and the export scanner reject the live host. There is no switch to turn | deliberate deviation (sandbox only is a product rule) | `pilot/client.py`, `copilot/core/send.py`, `tests/local/test_hosts_static.py` |
| 10 | Redirect URLs must be HTTPS | The order helpers use HTTPS placeholder URLs | meets | `tools/sandbox_orders.py`, `tools/sandbox_seed.py` |
| 11 | CSRF protection on order creation | Orders are created by a command-line script, not by a web route; every POST route of the app checks a CSRF token | meets | `copilot/web/security.py` |
| 12 | Handle webhooks; verify their signature | Proofie runs on the seller's machine with no public URL, so no webhook endpoint is switched on in the local app (the code is present behind a setting that is off): the state of a dispute is read from PayPal after every write and on a visible refresh. The hosted copy's Blueprint switches the receiver and its verification on (`verify-webhook-signature`, one verification per event, an unsigned event refused), pending the owner's registration of its address; until then it receives no events. The published guidance's dispute event names (`CUSTOMER.DISPUTE.CREATED`, `UPDATED`, `RESOLVED`) are the three names Proofie's code knows | deliberate deviation (polling, local-first) | `README.md` "What it is not" |
| 13 | Check a dispute's `links` and `allowed_response_options` before acting | Actions appear only when PayPal's latest response offers them: Proofie reads the dispute's `links` for every action. It does not read `allowed_response_options`; no code path uses that field. Proofie adds what the reference does not say: right after any seller write the dispute sits in `UNDER_REVIEW` with no action for a short while, and a second write in that window is refused by PayPal, so in that window the app does not send, reads again on request (Check again, Refresh) and never retries | partly meets (links are read; `allowed_response_options` is not) | `pilot/step3_dispute.py`, `copilot/core/send_service.py` |
| 14 | Lifecycle `INQUIRY` (up to 20 days) → `CLAIM` → `CHARGEBACK` → ... | Proofie never assumes a chain of stages: it shows the stage and status PayPal returns. In our own verification probes (scripts outside the published tree) a seller escalation moved a case from `INQUIRY` to `CHARGEBACK` directly (observed 2026-10-06); that is why nothing is derived from the chain. The dispute page's stage strip follows the same rule: it lists PayPal's four published stage names in the order of the pinned disputes schema and marks only the one PayPal returned; it derives and predicts nothing | meets (by not assuming) | `pilot/step3_dispute.py` |
| 15 | Add tracking with `POST /v2/shipping/trackers` | Proofie posts to `POST /v1/shipping/trackers` with a `trackers` array (the published Tracking API, section 5, row L2): the sandbox answered 201 to exactly that body on 2026-10-06 and the GET listed the tracker afterwards. In this release the sandbox setup script adds the test tracker, and the fulfilment feature registers a tracking with PayPal only after the seller approves the exact request shown on the page: one POST with its `PayPal-Request-Id`, the request fingerprint and PayPal's answer kept in the evidence, and the tracker read back by GET; registration does not prove delivery. Its row against the published contract is in section 4, with the 2026-10-12 read. | deliberate deviation (the v1 path is the one we verified) | `tools/sandbox_seed.py`, `copilot/features/fulfilment/register.py` |
| 16 | Evidence is multipart; check the dispute's `evidences` for what PayPal requested | The send builds one JSON `input` part plus one `evidence-file` part per attachment, matches PayPal's requested evidence, and confirms by a fresh GET that the content landed (real sandbox send, 2026-10-05). PayPal lists an attached document by its name only, so the attached files are confirmed by those listed names, counted as a multiset: a name must be listed at least as many times as it was attached, and a second file with the same name cannot be attached to one package (`verify_after_with_attachments` in `copilot/core/send.py`; how PayPal lists two same-name documents was never observed) | meets | `copilot/core/send.py`, `copilot/core/send_service.py` |
| 17 | Never automatically accept a claim without review | Accepting the claim is the seller's last option in Proofie's web page, offered while PayPal shows the action, after the seller types the amount phrase and approves the exact request; the model never suggests it and the MCP server has no such tool | meets | `docs/MCP.md` |
| 18 | Refund proactively to prevent escalation | Proofie shows what conceding and defending cost, with sources, and leaves the decision to the seller; it issues no refund; an offer or a message to the buyer is sent only when PayPal offers the option and the seller approves the exact request (this release) | deliberate deviation (the seller decides) | `copilot/features/resolution/` |
| 19 | Subscribe to dispute webhook events | In the local app, polling covers the one event that would matter (`RESOLVED`): the outcome page reads it from PayPal. The hosted copy is configured to receive dispute events once the owner registers its address; no subscription exists yet | deliberate deviation for the local app, pending for the hosted copy (see 12) | `copilot/features/outcome/` |

## 3. PayPal's public Postman workspace, where it differs from Proofie

Source: the collections "Add Tracking", "Transaction Search" and "PayPal APIs" of PayPal's public Postman workspace, read on 2026-10-06 (request names, paths, query names and example field names only; no environment, credential or script was read). Nine of the eleven paths Proofie calls appear there under PayPal's own request names. The two that do not:

| Point | PayPal's collections | Proofie | Verdict and reason |
|---|---|---|---|
| Tracking path form | POST `/v1/shipping/trackers-batch` to add trackers; GET `/v1/shipping/trackers/{tracking id}` to read one | POST `/v1/shipping/trackers` with a `trackers` array whose field names (`transaction_id`, `tracking_number`, `status`, `carrier`, `carrier_name_other`) are a strict subset of the ten the collection uses; GET `/v1/shipping/trackers?transaction_id=` to list a transaction's trackers | deliberate deviation: one tracker per transaction, confirmed by a read-back instead of trusting the POST's answer; the sandbox accepted the POST (201) and the list GET (200) on 2026-10-06. The published Tracking schema (section 5, row L2) defines both forms |
| Transaction Search query | `fields` as a comma list of seven named groups; `page_size` 100 | `fields=all` for the dispute's own transaction (one call per 31-day window, up to three windows); `fields=transaction_info` with `page_size=500` for the account's dispute-fee position | deliberate deviation: `all` and 500 are documented values of the published Transaction Search schema (section 5, row L3: `page_size` 1..500); the sandbox answered 200 to both on 2026-10-06. Every query name Proofie uses is one the collection offers |

## 4. Operations Proofie calls in this release, against the published schemas

Classes: **conformant** (shape and values in the schema), **tolerated** (the contract is silent or inconsistent and the sandbox accepted what Proofie sends; the sandbox fact is cited), **cosmetic** (a difference with no effect on the wire). Only field names and status codes are stated; no PayPal response content is reproduced here.

| Operation | What Proofie sends and reads | Class | Source that settles it |
|---|---|---|---|
| `POST /v1/oauth2/token` | client credentials, HTTP Basic, `grant_type=client_credentials`; reads `access_token` and `expires_in` | cosmetic (the authentication guide has no schema) | PayPal's authentication guide; every sandbox run since 2026-10-03 |
| `GET /v1/customer/disputes` | no filters; follows PayPal's own `next` link until exhausted, so neither deprecated paging parameter is used | conformant | disputes schema 1.12 (L1) |
| `GET /v1/customer/disputes/{id}` | reads `dispute_id`, `reason`, `status`, `dispute_life_cycle_stage`, `dispute_amount`, `disputed_transactions`, `create_time`, `update_time`, `seller_response_due_date`, `links`, `evidences`, `dispute_outcome`, and the top-level `messages` array (`posted_by`, `content`, `time_posted` of each message: a sent message is confirmed only when PayPal lists it); every path read exists in the schema | conformant | disputes schema 1.12 (L1) |
| `POST /v1/customer/disputes/{id}/provide-evidence` | multipart: one `input` part (JSON `evidences[]` with `evidence_type`, `evidence_info.tracking_info[]`, `notes` cut at 2000) plus `evidence-file` parts; the path comes from PayPal's own `provide-evidence` link and is checked for host, path and method; after the POST the read-back matches the attached files by PayPal's listed document names, counted as a multiset (`verify_after_with_attachments` in `copilot/core/send.py`) | tolerated: the schema lists only the file part while its prose and the sandbox use the JSON `input` | real sandbox send on 2026-10-05, confirmed by GET |
| same operation, `carrier_name` | the dispute contract's carrier codes pass through; a catalogue code the contract does not list, and any unknown carrier, go as `OTHER` plus `carrier_name_other` | conformant since 2026-10-08 | disputes schema 1.12 (L1), `copilot/core/carriers.py` |
| `GET /v1/reporting/transactions` | `start_date`, `end_date`, `transaction_id`, `fields`, `page_size`, `page`; reads `transaction_details[].transaction_info`, `shipping_info`, `total_pages`, `total_items`, `page` | conformant | Transaction Search schema 1.10 (L3); sandbox 200s on 2026-10-06 |
| `POST /v1/shipping/trackers` | `trackers[]` with `transaction_id`, `tracking_number`, `status`, `carrier`, optional `carrier_name_other` | conformant; cosmetic: the sandbox answers 201 where the contract documents 200 (the client accepts any 2xx) | Tracking schema 1.10 (L2); sandbox 201 on 2026-10-06 and on 2026-10-12 through the app's fulfilment page (one tracking; the POST line and the GET line in the evidence carry the same request and approval fingerprints, read back `SHIPPED`) |
| `GET /v1/shipping/trackers?transaction_id=` | reads `trackers[]` and, per tracker, `tracking_number`, `carrier`, `status`, `shipment_date`, `last_updated_time`, `links[].rel` | tolerated: the contract documents one tracker object, the sandbox returns a `trackers` list; `last_updated_time` is kept raw and never parsed as a date | sandbox 200 on 2026-10-06 and 2026-10-12 |
| `POST /v1/customer/disputes/{id}/send-message` | `message` (1 to 2000 characters; a text that contains "http", "www." or "@", in any case, a link or e-mail marker, is refused before the POST); the path is PayPal's own `send-message` link from a fresh read of the dispute, checked for host, path and method, so without that link nothing is sent; `PayPal-Request-Id` is derived from the dispute id and the request fingerprint (a UUIDv5), so the same content carries the same id, but PayPal did not deduplicate this operation by it in the sandbox (two identical sends produced two seller messages, observed 2026-10-16); Proofie's own send-once guard (the reservation of `copilot/core/write_guard.py`, taken before the POST) therefore refuses a second send of the same approved request before any second POST; the POST runs once, only when the approval fingerprint equals the request fingerprint; then `GET /v1/customer/disputes/{id}` reads the dispute back: at most two reads per pending row each time the resolution page or the sent-result page is opened (a poll, then a read-back once PayPal has settled), never a loop (`settle_pending` in `copilot/features/resolution/service.py`); Check again reads once per row (`check_rows` in the same file). The message counts as confirmed only when PayPal lists it; a row still settling 80 seconds after the send shows as not confirmed (`SETTLE_WINDOW_SECONDS`) | conformant | disputes schema 1.12 (L1); sandbox 200 on 2026-10-11 and 2026-10-12 (one message each through the app; on 2026-10-12 the POST line and every read-back line in the evidence carry the same request and approval fingerprints, read back `UNDER_REVIEW` once, then `WAITING_FOR_BUYER_RESPONSE`); the repeated send of 2026-10-16 (sandbox, through the app) is why the duplicate guard is Proofie's own |
| `POST /v1/customer/disputes/{id}/make-offer` | `offer_type` (always `REFUND`; the contract's three other types are never sent), `offer_amount` (`currency_code`, `value` built by code from integer cents, never above the disputed amount, in the dispute's currency), `note`; the path is PayPal's own `make-offer` link, checked as above; the same `PayPal-Request-Id` derivation, approval rules and send-once guard (the reservation of `copilot/core/write_guard.py`); after the read-back the offer counts as confirmed only when PayPal no longer offers `make-offer` | conformant (one of the schema's offer types) | disputes schema 1.12 (L1); sandbox 200 on 2026-10-11 (one offer through the app, read back `WAITING_FOR_BUYER_RESPONSE` with the offer link gone); the fingerprint fields in the evidence lines were added after that run and have not yet been exercised live for an offer |
| `GET /v2/checkout/orders/{id}` (setup scripts only) | reads `status` and `purchase_units[].payments.captures[]` (`id`, `status`, `amount`) | conformant | Orders schema 2.36 (L5) |
| link `rel` values | PayPal returns underscores (`provide_evidence`); the prose of the contract mostly spells hyphens; the contract fixes no spelling, so Proofie accepts both and canonicalises to hyphens | cosmetic | disputes schema 1.12 (L1); sandbox reads 2026-10-06 |

Enabled but not yet exercised against PayPal: `appeal`. It is on in this release; no sandbox dispute of ours has offered an appeal, so it has not been sent. It appears only when PayPal's fresh read of the dispute offers an appeal; it is sent once after the seller approves the exact request, through the same send-once reservation as the message, offer and tracker writes (`copilot/core/write_guard.py`, key: dispute, action and request sha256), and with active approval on it also has its own one-attempt receipt; the evidence attempt registry (`copilot/core/attempt_store.py`) is not used by the appeal. An uncertain answer is reconciled by reading the dispute, never by a second POST, and the result is stated only from PayPal's read-back. Not called in this release: `verify-webhook-signature` (its code is in the published tree behind a setting that is off). `send-message`, `make-offer` and the fulfilment feature's tracker registration are enabled in this release, each sent once after the seller approves the exact request (evidence is sent once per dispute, row 7); their rows are in the table above. `accept-claim`, `escalate`, `adjudicate` and the other dispute write operations are not called by Proofie's code.

## 6. What this page does not claim

- No production result: everything was observed in the PayPal sandbox, with one sandbox seller account, on the dates stated.
- No universality: a sandbox answer observed once (the tracker 201, the stage jump in row 14) is a fact about that run, not a promise about PayPal's production behaviour.
- No comparison: this page says what Proofie does; it ranks nothing.
